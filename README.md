# img2txt Description Service

Эта ветка репозитория содержит сервис генерации клинического описания
дерматоскопического изображения. Это отдельный внутренний компонент, который
работает в составе основного приложения
[`skin-cancer-ai`](https://github.com/OdincovMD/skin-cancer-ai).

## О проекте

Сервис решает одну конкретную задачу: формирует итоговое русскоязычное
клиническое описание по данным дерматоскопического случая. Это не монолитное
приложение для всего диагностического контура.
Его зона ответственности ограничена обработкой изображения и маски, извлечением
и ранжированием признаков, подготовкой данных для генерации текста и возвратом
результата во внешнюю систему.

Выделение этого процесса в отдельный сервис даёт несколько практических
преимуществ:

- отделение вычислительной обработки и генерации текста от основного backend
- изоляцию зависимостей на checkpoint-модель и LLM API
- собственное хранилище состояния задачи и промежуточных статусов
- асинхронную интеграцию с внешним этапом классификации

## Что делает сервис

В рабочем контуре сервис:

- принимает исходное изображение и бинарную маску очага
- извлекает цветовые, геометрические, текстурные и производные признаки
- преобразует численные признаки в категориальные бакеты
- ранжирует наиболее значимые признаки с помощью checkpoint-модели
- сохраняет и отдаёт не только важные признаки, но и полный набор рассчитанных
  лейблов
- принимает результат внешней классификации отдельным запросом
- объединяет признаки и классификацию в единый контекст для генерации
- генерирует итоговое описание через внешний LLM API
- отправляет результат обратно в backend через callback endpoint

Сервис использует двухфазную схему обработки в обычном режиме:

1. после загрузки изображения и маски выполняется этап извлечения признаков
2. после поступления классификации запускается этап генерации описания

Такая схема убирает жёсткую синхронную связность между выделением признаков,
классификацией и генерацией текста. В режиме `features_only=true` сервис
работает по укороченному сценарию и завершает работу после расчёта признаков.

## Как работает в системе

Сервис не строит маску самостоятельно и не выполняет первичную классификацию.
Эти данные приходят из внешнего приложения. Внутри общего контура он работает
как специализированный обработчик с HTTP API и локальным состоянием задачи.

Полный поток выглядит так:

```text
image + mask
    -> feature extraction
    -> feature bucketing
    -> importance ranking
    -> classification merge
    -> LLM generation
    -> callback to backend
```

Внешняя система остаётся источником `job_id`, классификации и конечного
потребления результата. Сервис берёт на себя только построение текстового
описания и управление собственным жизненным циклом задачи.

## Какие данные возвращает сервис

После этапа обработки изображения сервис сохраняет и может вернуть три
набора признаков:

- `important_labels`: топ-N наиболее значимых признаков после ranking-модели;
  это компактный список, который используется как основной контекст для
  генерации описания
- `all_labels`: полный набор рассчитанных категориальных лейблов в формате
  `feature:value`
- `bucketed_labels`: тот же полный набор, но в плоском bucket-формате
  `bucket_<feature>:value`, который соответствует входу ranking-модели и
  удобен для внешней аналитики

Примеры:

- `important_labels`: `shape:неправильная`
- `all_labels`: `delta_V_inner_rim:ободок:темнее_центра`
- `bucketed_labels`: `bucket_delta_V_inner_rim:ободок:темнее_центра`

По смыслу признаки делятся на несколько групп:

- форма и размер: `shape`, `elongation`, `eccentricity`, `area`, `perimeter`
- границы и контур: `borders`, `asymmetry`, `rim`, `fractal_dimension`,
  `convexity`, `solidity`, `extent`, `radial_variance`,
  `perimeter_area_ratio`
- цветовой паттерн: `contrast`, `palette`, `pigmentation`,
  `color_homogeneity`, `dominant_hue`, `color_distance_euclidean`,
  `color_balance_*`, `delta_*`, `percent_*`, `entropy_*`, `std_*`,
  `mean_*`
- текстура и структура: `texture`, `texture_coarseness`, `structure_order`,
  `glcm_*`, `lbp_*`, `lobulation`

Если при создании задачи передан флаг `features_only=true`, сервис завершает
обработку после расчёта этих наборов признаков, не ждёт внешнюю классификацию
и не строит финальный текст.

## Архитектура

Код сервиса расположен в каталоге `service/` и разбит на функциональные слои:

- `routers` реализует HTTP API и координирует входящие запросы
- `core` содержит конфигурацию, проверку токена, callback и вспомогательную
  логику обработки задач
- `db` инкапсулирует SQLite, ORM-модели и операции чтения/записи состояния
- `pipeline.py` связывает вычислительные этапы в единый сценарий обработки
- `pipeline_steps` содержит отдельные шаги извлечения признаков, бакетизации,
  ранжирования и генерации

Подробное описание модулей и потоков данных вынесено в
[docs/architecture.md](docs/architecture.md).

## Технические свойства и ограничения

- Сервис рассчитан на внутреннее использование и закрытый API с токеном.
- Хранилище состояния построено на SQLite и подходит для одного сервисного
  контура, но не является целевой конфигурацией для распределённых сценариев с
  высокой конкуренцией запросов.
- Для ранжирования признаков требуется checkpoint модели по пути
  `IMPORTANCE_CHECKPOINT_PATH`.
- Для генерации текста требуется внешний LLM API и корректный `GROQ_API_KEY`.
- Если backend по `CALLBACK_URL` недоступен из Docker-сети, задача завершится с
  ошибкой callback, даже если текст уже успешно сгенерирован.
- Сервис не выполняет построение маски и не выполняет этап внешней
  классификации.
