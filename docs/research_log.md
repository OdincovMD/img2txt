# Исследовательский лог: модель важности признаков (img2txt)

Документ фиксирует ход экспериментов по обучению модели ранжирования важных признаков дермоскопических изображений (Шаг 3 пайплайна img2txt). Предназначен как черновая база для научной работы.

**Дата последнего обновления:** 2026-04-11

---

## 1. Постановка задачи

### 1.1. Контекст
img2txt — пайплайн из 4 шагов: (1) сегментация + извлечение 60+ численных признаков, (2) перевод в категориальные метки по пороговым правилам, (3) **ранжирование «важных» признаков нейросетью**, (4) генерация клинического текста LLM (Mistral-7B). Шаг 3 — узкое место: от качества top-k ранжирования зависит, какие признаки попадают в финальное описание.

### 1.2. Задача Шага 3
Multi-label ranking: по изображению (RGB, опционально + бинарная маска очага) предсказать топ-k признаков из фиксированного словаря (`LABEL_NAMES`, `NUM_LABELS=56`), которые врач-эксперт счёл бы диагностически значимыми.

- **Вход:** изображение 224×224, опционально 4-й канал — маска очага от YOLO.
- **Выход:** вектор вероятностей длины `NUM_LABELS`, из которого берётся top-k.
- **Метрика:** Precision@k, Recall@k при k=10 (среднее число экспертных меток на изображение ≈ 10 → P@10 = R@10).
- **Функция потерь:** BCE с логитами (multi-label).

### 1.3. Данные
- **Экспертная разметка:** ~200 изображений, по каждому эксперт выбирал до 10 важных признаков из 56.
- **Псевдо-разметка:** сгенерирована автоматически (`importance/pseudo_importance.py`) по комбинации z-score отклонения признака от популяции и приоритета признака. Несколько тысяч изображений.
- **Разметка сейчас ведётся вручную** через мини-приложение `annotation/` (Flask + vanilla JS), создаёт `annotations.csv` с колонками `image_path`, `important_labels` (JSON).

## 2. Архитектура модели

- **Файл:** [importance/importance_model.py](../importance/importance_model.py)
- **Бэкбон:** `efficientnet_b0` (по умолчанию), также поддерживаются `resnet18`, `resnet34`.
- **Вход:** 3 или 4 канала (RGB или RGB+маска). При 4 каналах — первый conv-слой бэкбона расширяется (копия RGB-весов + нулевая инициализация 4-го канала).
- **Голова:** GAP → Dropout → Linear(NUM_LABELS).
- **Чекпоинт:** сохраняется как `{"model_state_dict": ..., "args": ...}`.

## 3. Хронология экспериментов

Ниже — упорядоченный список ключевых итераций с краткой мотивацией, изменениями и результатом. Все числа — best val P@10 = R@10 (val = 30 изображений, фиксированный seed).

### 3.1. Базовый бейзлайн (старт)
- **Конфиг:** efficientnet_b0, 224×224, BCE, Adam lr=1e-4, weight_decay=1e-4, dropout=0.2, без масок, ~2500 псевдо + 200 реальных.
- **Результат:** ~0.40, плато после 15-20 эпох.
- **Наблюдение:** train loss падает, val P@10 стоит → переобучение + дисбаланс реального и псевдо-сигнала.

### 3.2. Попытка №1 — pos_weight + focal loss
- **Мотивация:** multi-label с сильным дисбалансом меток (редкие признаки — 1-2% положительных).
- **Изменения:** добавлены `use_pos_weight`, `pos_weight_cap=10`, `loss_type="focal"`, `focal_gamma=2`, `weight_decay=1e-3`, `dropout=0.4`.
- **Результат:** ~0.40 → **0.45** при pos_weight включённом, focal без эффекта.
- **Важный урок (позже):** **pos_weight вреден для top-k ранжирования**. Он смещает абсолютные вероятности редких меток вверх, но top-k смотрит на *порядок*, а не на калибровку. На следующих итерациях pos_weight был отключён и это дало прирост.

### 3.3. Попытка №2 — добавление псевдо-разметки с балансировкой
- **Мотивация:** 200 реальных мало, хочется использовать ~2500 псевдо-меток.
- **Изменения:** `WeightedRandomSampler` с `real_fraction_in_batch=0.5` (в каждом батче половина — реальные, половина — псевдо), `epoch_size = n_real * 4`.
- **Результат:** **падение до 0.05**.
- **Диагноз:** распределение псевдо-меток принципиально отличается от экспертного. Псевдо-алгоритм ориентируется на z-score отклонения от популяции, а эксперт — на клиническую значимость. Смешивание ломает сигнал.
- **Вывод:** псевдо-разметка в текущем виде — **не пригодна** как замена/дополнение к экспертной для top-k задачи. Оставлена опция `pseudo_subsample` для контролируемого эксперимента, но по умолчанию выключена.

### 3.4. Попытка №3 — сегментационные маски как 4-й канал
- **Мотивация:** дать модели явный prior о локализации очага, чтобы не тратить capacity на поиск ROI.
- **Изменения:**
  - Добавлен helper [core/segmentation.py::segment_with_loaded_yolo](../core/segmentation.py) — батчевая генерация масок без перезагрузки YOLO на каждый вызов.
  - Кэширование масок в `masks_cache/{image_id}_mask.png`.
  - В [importance/importance_dataset.py](../importance/importance_dataset.py) — предзагрузка масок в contiguous numpy-кэш, конкатенация как 4-й канал.
  - Модель адаптирует первый conv-слой под 4 канала (копия RGB + нулевая инициализация mask-канала).
- **Результат:** 0.5100 → **0.5133** (в пределах шума val=30, ±0.02).
- **Вывод:** маски не дают статистически значимого прироста. EfficientNet и так находит очаг на 224×224. Возможно, маски помогли бы на более высоких разрешениях или при меньшей модели.

### 3.5. Попытка №4 — корректная аугментация
- **Мотивация:** после регрессии к 0.23 в одной из итераций пользователь задал вопрос «может ты переборщил с аугментацией?».
- **Изменения:** добавлен параметр `aug_strength: Literal["mild","strong"]`.
  - `mild`: RandomResizedCrop(0.92-1.0), rot=15°, ColorJitter(0.15/0.15/0.10, **hue=0**).
  - `strong`: crop(0.8-1.0), rot=30°, ColorJitter(0.3/0.3/0.2/0.05).
- **Ключевой момент:** **hue shift ломает сигнал по цветовым меткам** (палитра очага диагностически значима — коричневый vs чёрный vs красный). В дерматоскопии hue=0 обязателен.
- **Результат:** `mild` стабильно лучше `strong` на этом датасете. С `mild` + правильными параметрами (batch_size=64, wd=5e-4, dropout=0.3, без pos_weight) — **0.51**.

### 3.6. Текущее лучшее состояние
- **Скор:** ~0.51 P@10=R@10.
- **Конфиг:**
  - efficientnet_b0, RGB (или RGBA — без разницы), 224×224.
  - BCE **без** pos_weight, без focal.
  - Adam lr=1e-4, weight_decay=5e-4, dropout=0.3, batch_size=64.
  - Только реальная разметка (200 изображений), без псевдо.
  - aug_strength=`mild`, hue=0.
  - val=30 (фиксированный seed).

## 4. Технические проблемы и их решения

### 4.1. Утечка RAM (~100 MB/батч)
- **Симптом:** при длительном обучении RSS процесса растёт линейно, на ~30-й эпохе OOM.
- **Диагностика:** добавлен `tracemalloc` с фоновым потоком, снимающим топ-15 аллокаторов и top-3 трейсбэка каждые 30с ([notebooks/img2txt2.ipynb](../notebooks/img2txt2.ipynb)).
- **Результат диагностики:** Python-heap стабилен (~920 MB), но RSS растёт (2552→3734→3964 MB). Утечка — в C/C++-библиотеках (Pillow, возможно DataParallel `replicate.py`), невидима для tracemalloc.
- **Решения:**
  1. `pin_memory=True` + `num_workers=0` — известный паттерн утечки host-буфера. Исправлено: `pin_memory = num_workers > 0`.
  2. Фрагментация glibc-malloc — добавлен `_malloc_trim()` через ctypes, вызывается периодически в train/val циклах. Возвращает свободные страницы ОС.
  3. Явный `del` + `gc.collect()` в конце эпохи.
  4. **Contiguous numpy-кэш изображений** — один большой массив `(N, H, W, 3)` uint8 вместо N отдельных PIL-объектов. Избегает fork-COW и миллионов мелких аллокаций. Реализовано в [importance/importance_dataset.py::_preload](../importance/importance_dataset.py).

### 4.2. Ошибка `'numpy.ndarray' has no attribute 'seek'`
- **Причина:** `core/segmentation.py::main()` вызывался с numpy-массивом вместо пути к файлу. YOLO ожидает путь или PIL-объект.
- **Вторая проблема:** YOLO + UNet перезагружались на каждый вызов при батчевой генерации масок.
- **Фикс:** добавлен [core/segmentation.py::segment_with_loaded_yolo](../core/segmentation.py) — принимает уже загруженную YOLO-модель и путь к изображению.

### 4.3. Ошибка `cannot select an axis to squeeze out which has size not equal to one`
- **Причина:** `transform_4ch` ожидал 4 канала, но `ImportanceDataset` молча возвращал 3 канала, если маска отсутствовала.
- **Фикс:** [importance/importance_dataset.py::__getitem__](../importance/importance_dataset.py) всегда производит 4-канальное изображение при `use_mask_channel=True`, подставляя нулевую маску при её отсутствии. Также добавлен флаг `_has_mask` для отслеживания реально загруженных масок.

### 4.4. Регрессия к 0.23 после успешного 0.45
- **Причина:** при перезапуске часть параметров не была передана явно, упали к дефолтам (`batch_size=16`, `wd=1e-3`, `dropout=0.4`), а успешный ран был на `batch_size=64, wd=5e-4, dropout=0.3`.
- **Урок:** все hyperparams должны быть явно зафиксированы в конфиге/ноутбуке, нельзя полагаться на дефолты функции.

## 5. Текущие ограничения и гипотезы

### 5.1. Потолок при 200 аннотациях
- Реалистичная оценка: **0.55-0.57** при текущем датасете.
- val=30 даёт шум ±0.02 на метрике — выигрыши меньше этого статистически незначимы.

### 5.2. Слишком большое пространство меток
- **Наблюдение пользователя (2026-04-11):** при ручной разметке всегда выбирается один и тот же пул ~25 признаков из 56. Остальные — «мёртвые» метки, которые модель не может выучить (нет положительных примеров) и которые разбавляют BCE-лосс.
- **Гипотеза:** урезание `LABEL_NAMES` до реально используемых (частота > 3-5%) даст прирост больше, чем маски/TTA.
- **План:** после завершения разметки построить гистограмму частот, выкинуть метки с частотой < 3%, снизить top_k с 10 до 5-7 пропорционально.

### 5.3. Качество псевдо-разметки
- Текущий алгоритм на основе z-score не согласован с экспертом. Варианты:
  - Пересобрать псевдо-разметку **после** обучения модели на реальных данных (self-training).
  - Использовать псевдо только для pre-training бэкбона (contrastive/supervised), дофайнтюн на реальных.
  - Отказаться от псевдо в пользу большего объёма ручной разметки.

## 9. Остальные шаги пайплайна

Предыдущие разделы сфокусированы на Шаге 3 (модель важности). Ниже — документация остальных компонентов системы, необходимая для полноты описания в научной работе.

### 9.1. Шаг 1 — извлечение признаков

**Файлы:** [core/features.py](../core/features.py), [core/segmentation.py](../core/segmentation.py), [extraction/feature_extraction_batch.py](../extraction/feature_extraction_batch.py)

#### Сегментация очага
Двухступенчатая схема:
1. **YOLO (основной)** — `ultralytics.YOLO` с весами `mask_builder_yolo.pt`, `retina_masks=True`. Возвращает полигоны → `cv2.fillPoly` → бинарная маска в разрешении оригинала.
2. **UNet (fallback)** — собственная реализация энкодер-декодер ([core/segmentation.py::UNet](../core/segmentation.py)) с 4 уровнями пулинга (64→128→256→512→1024 каналов), BatchNorm+ReLU, `nn.Upsample` в декодере, выход 1 канал + сигмоид. Используется только если YOLO не нашёл ни одной маски.

Выход: бинарная маска uint8 в размере исходного изображения.

#### Извлекаемые признаки
Всего ~60 численных признаков, сгруппированы в 5 блоков:

**Глобальный цвет** ([core/features.py::extract_global_color_features_with_mask](../core/features.py)):
- Средние и std по HSV внутри очага (`mean_H/S/V_lesion`, `std_H/S/V_lesion`).
- Баланс BGR-каналов (`color_balance_R/G/B`).
- Энтропия гистограмм H/S/V (`entropy_H/S/V_lesion`).
- Расстояние очаг↔кожа в LAB: евклидово (`color_distance_euclidean`) и ΔE2000 (`color_distance_deltaE`) — перцептуально-равномерное.
- KMeans по HSV на 3 кластера → `dominant_colors_lesion` (используется в палитровой метрике).
- Доли пикселей: тёмных (`percent_dark_pixels`, V<50), белых (`percent_white_pixels`, V>200 & S<30), красных (`percent_red_pixels`, H<15 или H>165 & S>50), синих (`percent_blue_pixels`, 90<H<140 & S>50).

**Локальный цвет** ([core/features.py::extract_local_color_features_with_mask](../core/features.py)):
- Градиенты центр↔периферия (маска `rr < 0.5 * r_max`): `delta_H/S/V_center_periphery`.
- Градиенты левая↔правая, верх↔низ (`delta_V/S_left_right`, `delta_V/S_top_bottom`) — базис правила ABCD (асимметрия).
- Градиент центр↔ободок (`delta_V_inner_rim`, rr≥0.8·r_max).
- Доли аномально ярких/тёмных пикселей (±2σ от среднего V).

**Форма** ([core/features.py::extract_shape_features](../core/features.py)): `area`, `perimeter`, `perimeter_area_ratio` (нормированный P/√A), `circularity` (4πA/P², 1 = круг), `aspect_ratio` (bbox), `eccentricity`, `solidity` (A/A_convex), `extent` (A/A_bbox).

**Граница** ([core/features.py::extract_border_features](../core/features.py)):
- `radial_variance` — дисперсия радиуса от центроида до точек контура (мера «рваности»).
- `convexity` — P/P_convex (отношение периметра к выпуклой оболочке).
- `fractal_dimension` — box-counting метод ([_boxcount](../core/features.py)), наклон логарифмической регрессии log(count) vs log(1/size).

**Текстура** ([core/features.py::extract_texture_features](../core/features.py)):
- GLCM (grey-level co-occurrence matrix) по скимиджу с квантованием до 16 уровней, distances=[1,2,4], 4 угла: `glcm_contrast`, `glcm_homogeneity`, `glcm_energy`, `glcm_entropy`.
- LBP (local binary patterns) uniform, P=8, R=1: `lbp_uniformity`, `lbp_entropy`, `lbp_mean`, `lbp_std`, `lbp_median`.

#### Формат выхода
- `features_json` — строка JSON со структурой `{color: {local, global}, shape, border, texture}`. Каждое значение — тройка `[russian_name, value, unit]` для человекочитаемости.
- Плоские колонки на каждый feature (для удобства статистики).
- `status` — строка успех/ошибка.

#### Публичное API
- `images_to_df(image_dir, recursive=False)` — сканирует директорию, строит df с `image_path`, `image_id`, `filename`.
- `extract_features_batch(df, yolo_weights, unet_weights)` — основной вход.

### 9.2. Шаг 2 — бакетизация признаков

**Файлы:** [analysis/threshold_rules.py](../analysis/threshold_rules.py), [config/threshold_config.py](../config/threshold_config.py), [analysis/feature_bucketing_batch.py](../analysis/feature_bucketing_batch.py)

#### Идея
Численные признаки Шага 1 → категориальные метки («слабая асимметрия», «границы ровные», «палитра богатая», ...), которые затем становятся словарём `LABEL_NAMES` для Шага 3 и попадают в промпт LLM на Шаге 4.

#### Два типа правил

**1. Простые пороги** (`THRESHOLDS` в [config/threshold_config.py](../config/threshold_config.py))
Каждому признаку сопоставлен список `[(threshold, label), ...]`, применяется функцией `apply_threshold`. Пример: `circularity → ["круглая"/"умеренно круглая"/"неправильная"]` по отсечкам.

**2. Составные правила** (функции `_xxx` в [analysis/threshold_rules.py](../analysis/threshold_rules.py))
Несколько признаков → одна метка. Ключевые:

| Правило | Признаки | Логика |
|---|---|---|
| `_asymmetry` | Σ\|Δ_H/S/V по центр-периферия, л-п, в-н\| | Правило A из ABCD. Порог — `asymmetry_agg`. |
| `_borders` | `circularity` + `perimeter_area_ratio` | «ровные» / «умеренно неровные» / «фестончатые». Правило B. |
| `_palette` | `dominant_colors_lesion` | Подсчёт «визуально различных» оттенков через `_compute_palette_variety`: сортировка H, счёт разницы >15°. |
| `_pigmentation` | `percent_dark/red/blue/white_pixels` | Приоритизация: белые > красно-синие > темнота. |
| `_elongation` | `aspect_ratio` + `eccentricity` | Линейная комбинация как score. |
| `_color_homogeneity` | `std_H/S/V + entropy_H` | Нормированная сумма. |
| `_lobulation` | `radial_variance + convexity + perimeter_area_ratio` | Score ∈ [0,1], три уровня. |
| `_dominant_hue` | `mean_H` + корректировка через `color_balance_R/G` | Основной оттенок + override на «зеленоватый». |
| `_pigment_inclusions` | `percent_red/blue/white_pixels` | Список включений (а не строка). |
| `_rim` | `delta_V_inner_rim` | Светлый/тёмный ободок по знаку Δ. |

#### Калибровка порогов
Пороги задавались вручную на основе визуального анализа распределений по датасету + консультаций с дерматологом (исходная предыстория, до текущего цикла экспериментов). Константы в `SCALAR` dict.

**Ограничение:** пороги фиксированные, не адаптируются к домену (кожа разных типов, разные дерматоскопы). Потенциальный путь улучшения — адаптивная бакетизация по квантилям датасета, но это сломает воспроизводимость между запусками.

#### Публичное API
- `features_to_labels(features: dict) -> dict` — один образец.
- `row_to_labels(row)` — обёртка для `df.apply`.
- `bucket_features_batch(df)` — батчевый вход, добавляет колонки `labels`, `features_organized`, `labels_json`.

### 9.3. Шаг 3 bis — псевдо-разметка

**Файл:** [importance/pseudo_importance.py](../importance/pseudo_importance.py)

#### Мотивация
До начала ручной разметки единственный способ получить целевой вектор важности — эвристика. Идея: «важный признак» ≈ «признак, сильно отклоняющийся от популяции».

#### Два сигнала

**1. Робастный z-score по датасету**
Для каждого скалярного признака `k ∈ LABEL_NAMES ∩ FEATURE_ROUTING` считается:
```
z_k(i) = (x_k(i) - median_k) / (MAD_k + eps)
```
где MAD — median absolute deviation. Чем выше `|z|`, тем больше вклад метки `k` в скор важности для изображения `i`.

**2. Приор по метаданным классификатора**
Ключевые слова из полей `diagnosis / structure / properties` (если уже есть классификация) добавляют фиксированные веса к определённым меткам. Примеры:
- «ретикуляр*» → +1.0 к `texture`, +0.9 к `pigmentation`
- «симметрич*» → +1.2 к `asymmetry`
- «бесструктур*» → +1.1 к `structure_order`

#### Комбинирование
`mode="combined"` (по умолчанию): итоговый скор = `z_weight * |z|_normalized + prior_weight * meta_prior`. Top-k по этому скору → список `"feature:value"` строк в формате, совместимом с экспертной разметкой.

#### Статус
**Эмпирически не подходит для обучения top-k ранкера.** См. раздел 3.3: смешивание псевдо-разметки с экспертной ломает метрику с 0.40 до 0.05. Гипотеза: распределение «что статистически отклоняется» ≠ «что клинически значимо». Оставлена в кодовой базе как инструмент pre-training / анализа, но не используется в основном обучении.

### 9.4. Шаг 4 — генерация клинического описания

**Файл:** [generation/description_inference.py](../generation/description_inference.py)

#### Модель
**Qwen2.5-7B-Instruct** (HuggingFace `Qwen/Qwen2.5-7B-Instruct`). Загружается в `torch.float16` на GPU с `device_map="auto"`. Кэшируется глобально (`_model_cache`), чтобы при батчевой генерации не перезагружать веса.

> **Примечание:** в `CLAUDE.md` и некоторых docstring упомянут Mistral-7B, но фактически используется Qwen2.5-7B. Расхождение — исторический артефакт, на работу системы не влияет. В научной работе указывать именно Qwen2.5-7B.

#### Промпт-инженерия

**System prompt** ([generation/description_inference.py::_SYSTEM_PROMPT](../generation/description_inference.py)) содержит жёсткие запреты:
1. Только русский язык.
2. Ровно 3-5 предложений, клинический стиль.
3. **Запрещено** ставить диагноз или упоминать названия заболеваний.
4. **Запрещено** давать рекомендации.
5. Использовать только предоставленные данные, не додумывать.

Это принципиально: модель не должна подменять врача — она формирует *наблюдательное описание*, а окончательный диагноз ставит специалист.

**User prompt** собирается в `_build_messages`:
- Пронумерованный список топ-k важнейших признаков от Шага 3 в виде `"{русское_описание}: {значение}"`.
- Опциональный блок классификации (`feature_type`, `structure`, `properties`, `final_class`), если в df есть колонка с `ClassificationResult`.
- Требования по формату (повторение ограничений из system prompt).

#### Параметры генерации
- `temperature=0.4` — низкая, чтобы текст был стабильным и не галлюцинировал.
- `top_p=0.85`, `repetition_penalty=1.15`, `do_sample=True`.
- `max_new_tokens=256` — достаточно для 3-5 предложений клинического стиля.

#### Интеграция с Шагом 3
Вход — список `important_labels` из Шага 3 (уже отфильтрованный top-k). Функция `_parse_feature_entries` раскрывает `"feature:value"` через `FEATURE_ROUTING`, получая человекочитаемое русское описание признака.

#### Публичное API
`generate_descriptions_batch(df, classification_col="classification", ...)` — добавляет колонку `description`. Graceful fallback если `transformers` не установлен или при ошибке генерации.

### 9.5. Инфраструктура: приложение ручной разметки

**Файл:** [annotation/app.py](../annotation/app.py), шаблоны в [annotation/templates/](../annotation/templates/), статика в [annotation/static/](../annotation/static/)

#### Архитектура
Flask + vanilla HTML/JS/CSS. Single-page app. Без фреймворков, без сборки.

#### Источники данных для UI
- `LABEL_NAMES` из [config/importance_config.py](../config/importance_config.py) — словарь 56 меток.
- `FEATURE_ROUTING` из [config/config.py](../config/config.py) — даёт категорию и русское описание для простых признаков.
- `_COMPOUND_LABELS` в [annotation/app.py](../annotation/app.py) — маппинг категорий и русских названий для составных меток (asymmetry, borders, palette, и т.д.), которые не входят в `FEATURE_ROUTING`.

#### UI-решения
- Метки сгруппированы по 6 категориям (Общие, Цвет глобальный, Цвет локальный, Форма, Граница, Текстура).
- Каждая метка показана как чекбокс с подписью `"{русское_описание}: {значение_из_бакетизации}"`.
- **Лимит в 10 чекбоксов технически enforced** — после 10 выбранных оставшиеся блокируются. Это отражает формат экспертной разметки (ровно top-10).
- Ранее сохранённые аннотации предвыбраны при возврате к изображению.
- Keyboard: Enter = сохранить, стрелки = навигация, что критично для скорости разметки (~25 кликов × 200 изображений).

#### Формат выхода
CSV `annotations.csv`:
- `image_path`: string
- `important_labels`: JSON-строка, например `["asymmetry:умеренная", "texture:неоднородная", ...]`

**Атомарная запись:** через temp-файл + `os.replace`, чтобы при падении процесса не потерять накопленную разметку.

**Резюмирование:** при старте загружает существующий `annotations.csv` и пропускает уже размеченные `image_path`.

#### Запуск
```bash
python annotation/app.py --csv features_dataset_bucket.csv --output annotations.csv --port 5050
```

## 10. Выводы для научной работы

1. **Экспертная разметка незаменима.** Псевдо-разметка на z-score конфликтует с клиническим решением эксперта; её прямое смешивание в батче обрушивает метрику с 0.40 до 0.05.
2. **pos_weight вреден для top-k ранжирования.** Смещение калибровки редких классов не помогает задаче, где важен порядок, а не абсолютная вероятность.
3. **Hue shift запрещён в дерматоскопии.** Цвет очага (коричневый/чёрный/красный) — диагностический признак, и ColorJitter по hue его искажает. Aug должен быть `mild` с hue=0.
4. **Сегментационная маска как 4-й канал не даёт прироста** на efficientnet_b0 @ 224×224. Бэкбон и так находит ROI. Возможно, имеет смысл при больших моделях/разрешениях.
5. **Утечка RAM в long-running обучении** — не в Python-heap, а в C/C++ (glibc fragmentation, Pillow, DataParallel). Решается `malloc_trim` + отказом от `pin_memory` при `num_workers=0` + contiguous numpy-кэшем.
6. **Потолок при 200 аннотациях ≈ 0.51-0.57 P@10.** Основной путь роста — увеличение разметки или сжатие пространства меток до реально используемых.
