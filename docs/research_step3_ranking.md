# Шаг 3. Ранжирование важных признаков

**Основные файлы:** [model/model.py](../model/model.py), [model/inference.py](../model/inference.py), [model/config.py](../model/config.py), [model/run.py](../model/run.py), [model/mlp.py](../model/mlp.py), [model/mlp_inference.py](../model/mlp_inference.py), [model/mlp_run.py](../model/mlp_run.py)

## Роль шага

Шаг 3 является центральным местом всего пайплайна. Именно здесь система
переходит от полного набора признаков к **приоритетному списку клинически
важных меток**, который потом используется для генерации текста.

После шага 2 у нас уже есть:

- численные признаки;
- бакетизированные клинические метки;
- структурированное описание случая.

Но пока еще непонятно, какие из этих признаков действительно должны войти в
финальный top-k.

Именно это решает шаг 3.

Он отвечает на вопрос:

> какие признаки из полного словаря врач, скорее всего, счёл бы наиболее
> важными для описания именно этого случая

## Постановка задачи

Формально шаг 3 решается как задача **multi-label ranking**.

Для каждого случая модель должна:

1. оценить важность каждой целевой метки;
2. отсортировать их по score;
3. вернуть top-k наиболее релевантных признаков.

То есть здесь ищется не один лучший класс и не полный бинарный вектор “есть /
нет”, а **упорядоченный приоритетный список признаков**.

Рабочие метрики шага:

- `Precision@10`
- `Recall@10`

Внутренне использовалась агрегированная оценка как среднее этих двух метрик на
валидации.

## Данные для обучения

Шаг 3 опирался на два типа supervision.

### Инструмент разметки

Для сбора экспертной разметки было сделано отдельное мини-приложение для
просмотра изображений и выбора важных признаков.

Основные файлы:

- [annotation/app.py](../annotation/app.py)
- [annotation/templates/index.html](../annotation/templates/index.html)
- [annotation/static/app.js](../annotation/static/app.js)
- [annotation/static/style.css](../annotation/static/style.css)

Логика этого инструмента была простой:

- врачу показывалось изображение случая;
- рядом отображался список доступных клинических признаков;
- эксперт отмечал те признаки, которые считал наиболее важными для описания;
- результат сохранялся в `annotations.csv`.

Это было не вспомогательное удобство, а критически важный слой всей системы,
потому что именно через это приложение формировался основной target для шага 3.

Смысл мини-приложения заключался в том, чтобы:

- собирать разметку в стандартизированном формате;
- ограничить выбор признаков рабочим словарем;
- получать сопоставимые top-k наборы между случаями;
- напрямую привязывать экспертное решение к конкретному изображению.

Именно благодаря этому инструменту шаг 3 обучался не на произвольных текстовых
описаниях и не на внешних диагнозах, а на явном выборе важных признаков как
отдельной целевой задаче.

### 1. Экспертная разметка

Основной источник истины — ручная разметка:

- `400` изображений;
- для каждого изображения эксперт выбирал до `10` важных признаков;
- разметка строилась в пространстве клинических меток, а не в пространстве
  “сырых” пикселей.

Именно этот слой определяет, что считается важным не статистически, а
прикладно и клинически.

### 2. Псевдо-разметка

Дополнительно использовалась автоматическая псевдо-разметка:

- на основе отклонения признаков от популяции;
- с добавлением эвристического приоритета отдельных свойств.

Идея была в том, чтобы использовать больше данных, чем доступно в ручной
разметке.

Однако это направление оказалось проблемным, потому что:

- статистически аномальный признак
- и клинически важный признак

не совпадают автоматически.

Именно это стало одним из главных уроков шага 3.

## Исходная нейросетевая постановка: только изображение

Первый класс подходов был image-based.

### Архитектура

Базовая постановка строилась вокруг CNN-бэкбона:

- `efficientnet_b0` как основной baseline;
- в инфраструктуре также поддерживались `resnet18` и `resnet34`;
- на вход подавалось RGB-изображение, а в отдельных экспериментах RGB+маска;
- на выходе модель предсказывала вектор вероятностей по всем целевым меткам.

Логика была простой:

- изображение содержит весь визуальный сигнал;
- модель сама должна научиться выбирать, какие признаки эксперт считает
  важными.

### Базовый результат

Первый бейзлайн быстро вышел на уровень порядка `0.40` и затем начал
платоировать.

Это сразу показало две вещи:

- задача решаема;
- но чистый image-only подход без дополнительных ограничений быстро упирается в
  потолок.

## Эксперименты внутри image-only ветки

### 1. Балансировка редких меток: `pos_weight` и focal loss

Поскольку задача multi-label и часть признаков встречается редко, естественной
идеей было усилить вклад редких положительных меток.

Пробовались:

- `pos_weight`;
- focal loss;
- более агрессивная регуляризация.

На одном из промежуточных этапов `pos_weight` локально улучшал результат
примерно с `0.40` до `0.45`, а focal loss почти не помогал.

Но дальше выяснился более важный эффект:

- `pos_weight` может повышать абсолютные вероятности редких меток;
- однако top-k ranking чувствителен прежде всего к **порядку** меток, а не к
  самой калибровке вероятностей;
- из-за этого `pos_weight` в итоговой ranking-задаче скорее вредил, чем
  помогал.

Главный вывод:

> для шага 3 важен порядок top-k, поэтому переусиление редких классов через
> `pos_weight` не даёт устойчивого преимущества

### 2. Псевдо-разметка как дополнительный supervision

Следующий большой эксперимент — смешивание экспертной и псевдо-разметки.

Мотивация была понятной:

- ручной разметки мало;
- псевдо-случаев можно получить существенно больше;
- значит, модель может увидеть больше примеров.

На практике получилось наоборот:

- качество резко ухудшалось;
- в одном из явных экспериментов метрика упала почти до `0.05`.

Причина оказалась принципиальной:

- псевдо-логика искала статистические отклонения;
- эксперт выбирал клинически значимые признаки.

Это не одно и то же. Поэтому псевдо-разметка оказалась плохим прямым
супервизором для top-k важности.

Вывод:

> псевдо-разметка в текущем виде непригодна как полноценная замена или прямое
> дополнение экспертной разметке

### 3. Сегментационная маска как дополнительный канал

Отдельно проверялась гипотеза, что модели поможет явный prior о локализации
очага:

- к RGB добавлялся четвертый канал;
- этим каналом служила бинарная маска сегментации.

Логика была такой:

- если модель заранее знает ROI,
- она может меньше тратить capacity на поиск очага
- и больше — на интерпретацию содержимого.

Фактически прирост оказался минимальным и оставался в пределах шума.

Из этого был сделан важный прикладной вывод:

- на разрешении порядка `224×224`;
- с `efficientnet_b0`;
- при данном масштабе данных

модель и без того достаточно хорошо локализует очаг.

То есть маска сама по себе не стала ключом к улучшению шага 3.

### 4. Аугментации и проблема цветового искажения

С image-only веткой был связан еще один важный урок: в дерматоскопии нельзя
обращаться с цветом как с нейтральным визуальным шумом.

Проверялись разные силы аугментаций:

- более мягкие;
- более агрессивные.

Критический вывод оказался таким:

- сильный `hue shift` ломает смысл задачи;
- цвет в дерматоскопии — это не декоративная характеристика, а диагностически
  значимая сущность;
- поэтому агрессивные цветовые искажения делают supervision менее согласованным
  с целью.

В результате лучшей оказалась мягкая схема аугментаций без hue shift.

Вывод:

> для шага 3 аугментации должны сохранять клинический смысл цвета, иначе
> модель учится на повреждённом сигнале

## Сжатие пространства меток

Это был один из самых сильных поворотных моментов шага 3.

Изначально модель училась на более широком словаре меток. После накопления
ручной разметки стало видно, что реально живым и стабильным оказывается только
подмножество категорий.

После анализа частот пространство было сжато до **24 активных меток**.

Это дало сразу несколько эффектов:

- задача стала проще;
- шумные и редкие цели ушли;
- supervision стал чище;
- табличные модели начали показывать существенно более сильные результаты.

Смысл этого перехода был не только в уменьшении размерности. Важнее было то,
что target space стал ближе к реальному словарю признаков, которым эксперт
действительно пользовался на практике.

## Мультимодальная ветка: изображение + признаки

После того как табличные признаки показали силу, возникла промежуточная
гипотеза:

> если изображение и структурированные признаки несут разный тип сигнала, их
> стоит объединить в одной модели

Так появилась мультимодальная схема:

- image branch на базе CNN;
- tabular branch для бакетизированных признаков;
- конкатенация эмбеддингов перед финальной головой.

Это был важный шаг, потому что он проверял не вопрос “лучше ли табличное
представление вместо изображения”, а вопрос “дают ли оба источника вместе
дополнительную силу”.

Результат оказался сильным:

- качество заметно выросло;
- лучший зафиксированный результат среди PyTorch-моделей дошел примерно до
  `0.61`.

Главный вывод из этой ветки:

- табличные признаки действительно несут огромную долю полезного сигнала;
- изображение при этом не бесполезно, но начинает играть скорее
  вспомогательную роль.

## Переход к чисто табличным моделям

После мультимодальной ветки следующий вопрос уже формулировался более
радикально:

> если большая часть полезной информации уже есть в признаковом пространстве,
> нужен ли image backbone вообще

Это привело к переходу на чисто tabular-подходы.

### Почему этот переход был логичным

На тот момент уже было видно:

- шаги 1 и 2 дают очень плотное описание очага;
- большая часть клинически значимой структуры уже выражена в признаках;
- изображение перестает быть единственным или даже главным носителем сигнала.

Следовательно, можно было попробовать полностью отказаться от тяжелой
нейросетевой обработки изображения и проверять, насколько далеко хватит
табличной модели.

## Tabular-ветка: CatBoost и XGBoost

На этом этапе проверялись градиентные бустинги по признаковому представлению.

### 1. CatBoost

CatBoost показал, что задача очень хорошо ложится на табличную постановку.

Он стал важным подтверждением общей гипотезы:

- проблема шага 3 не требует обязательного визуального backbone;
- уже извлечённые и правильно оформленные признаки обладают высокой
  предсказательной силой.

CatBoost дал сильный результат, но не стал финальным лидером.

### 2. XGBoost

Следующим и наиболее сильным табличным направлением стал XGBoost.

Изначально модель строилась как ансамбль независимых бинарных классификаторов:

- по одной модели на каждую целевую метку;
- каждая модель предсказывает собственный score важности;
- затем scores объединяются и сортируются в общий top-k.

Именно эта ветка стала лучшим практическим baseline проекта.

Лучший зафиксированный результат для независимых XGBoost-моделей был около
`0.62`, что оказалось выше, чем у тяжелой мультимодальной нейросети.

Это был очень сильный архитектурный вывод:

- визуальные эмбеддинги полезны;
- но на этой задаче они не обязательны;
- табличный бустинг уже способен решать ranking не хуже, а местами лучше.

## Разные пространства признаков для XGBoost

Внутри XGBoost-ветки отдельно исследовались разные наборы входных признаков:

- `numeric_only`
- `selected_buckets`
- `all_buckets`

Это был важный исследовательский слой, потому что вопрос стоял не только в
выборе алгоритма, но и в том, **какое именно представление случая** лучше
всего подходит для ranking.

Главные выводы здесь были такие:

- search space гиперпараметров нельзя считать универсальным между feature set;
- один и тот же checkpoint нельзя переносить между режимами без проверки;
- режимы отличаются не только числом признаков, но и характером сигнала.

То есть в шаге 3 оказалось важным не просто выбрать XGBoost, а согласовать:

- модель;
- feature space;
- target space;
- калибровку.

## MLP на табличных признаках

Помимо бустингов проверялась и нейросетевая табличная альтернатива — MLP.

Логика этой ветки была понятной:

- если задача всё же содержит зависимости между таргетами;
- и если табличное пространство уже хорошо подготовлено;
- то joint-модель на всех таргетах сразу может потенциально использовать эти
  зависимости лучше, чем независимые бинарные модели.

MLP остался отдельным и содержательно важным направлением:

- он подтверждает, что табличное пространство пригодно и для нейросетей;
- но в репозитории именно XGBoost оказался более сильным и более практичным
  рабочим направлением.

## Ограничение независимых XGBoost-моделей

Несмотря на силу XGBoost-бейзлайна, у него оставалось концептуальное
ограничение:

- каждая целевая метка предсказывается отдельно;
- модель не использует явные зависимости между теми важными признаками,
  которые часто встречаются совместно.

А для clinical importance это критично, потому что значимые признаки нередко
живут не поодиночке, а комбинациями.

Из этого ограничения естественно вырос следующий шаг.

## `xgb_classifier_chain`

Следующей гипотезой стало использование **classifier chain** поверх XGBoost.

Идея цепочки:

- первая модель предсказывает первую метку;
- вторая получает исходные признаки и предсказание первой;
- третья получает исходные признаки и предсказания первых двух;
- и так далее.

Такой подход позволяет встроить зависимости между таргетами прямо в процесс
ранжирования.

### Почему это важно

Для шага 3 это особенно естественно, потому что:

- важность клинических признаков часто коррелирует;
- некоторые признаки усиливают или ослабляют вероятность других;
- top-k лучше формируется, когда модель видит не только исходное описание
  случая, но и уже предсказанную структуру важных меток.

### Как решалась проблема leakage

Если просто подставлять train-предсказания предыдущих моделей, возникает
leakage: следующая модель видит слишком “чистый” сигнал.

Поэтому в chain-ветке используется более аккуратная схема:

- для train-time строятся OOF-предсказания;
- именно они добавляются как chain features;
- на inference цепочка разворачивается уже последовательно на реальных
  предсказаниях.

Это делает classifier chain архитектурно корректным и пригодным для
практического использования.

## Калибровка label bias

Отдельный слой внутри XGBoost-ветки — калибровка распределения выбираемых
меток.

Здесь решалась задача не “лучше классифицировать признак вообще”, а:

> как сделать так, чтобы top-k не системно пере- или недовыбирал отдельные
> метки

Для этого использовался bias на уровне логитов / score-пространства.

Смысл калибровки:

- приблизить распределение выбираемых признаков к реальному распределению
  положительных меток;
- уменьшить перекос в сторону переиспользуемых или недоиспользуемых категорий;
- сделать итоговый ranking более стабильным.

Это важный практический слой, потому что шаг 3 оптимизируется не только как
набор отдельных классификаторов, но и как система отбора top-k признаков в
целом.

## Текущее состояние шага

На сегодня логика шага 3 выглядит так:

1. image-only ветка доказала, что задача решаема, но быстро упирается в потолок;
2. псевдо-разметка в текущем виде оказалась плохим прямым supervision;
3. маска как дополнительный канал не дала значимого выигрыша;
4. аккуратные аугментации важны, а hue shift вреден;
5. сжатие target space до 24 активных меток оказалось критически важным;
6. мультимодальная схема показала силу табличных признаков;
7. чистые табличные модели оказались не слабее, а зачастую сильнее;
8. XGBoost стал главным практическим baseline;
9. classifier chain стал следующим логическим развитием этой ветки.

## Главные выводы по шагу 3

### 1. Экспертная разметка незаменима

Шаг 3 предсказывает не “редкость” и не “аномальность”, а клиническую важность.
Поэтому именно экспертный supervision определяет правильную целевую постановку.

### 2. Псевдо-разметка и клиническая важность не совпадают автоматически

Статистическое отклонение признака от популяции само по себе не означает, что
этот признак эксперт вынесет в top-k.

### 3. Цветовой сигнал нельзя портить агрессивными аугментациями

Для дерматоскопии цвет — часть предметной истины, а не просто визуальная
вариация.

### 4. Табличное представление оказалось сильнее, чем ожидалось

Шаги 1 и 2 дали настолько плотное описание случая, что табличные модели смогли
конкурировать с тяжелыми визуальными архитектурами.

### 5. Сжатие словаря меток критично

Сокращение пространства целей до реально используемого словаря дало один из
самых сильных улучшений во всем проекте.

### 6. Чистый бустинг стал основным практическим направлением

XGBoost оказался не временным упрощением, а полноценным и сильным решением
задачи шага 3.

### 7. Следующий логический уровень — моделировать зависимости между метками

Именно из этого вырос `xgb_classifier_chain`, который делает шаг 3 не просто
набором независимых классификаторов, а более связной ranking-системой.

## Детали реализации image-only ветки

### Архитектура модели

- **Файл:** [model/model.py](../model/model.py)
- **Бэкбон:** `efficientnet_b0` по умолчанию, поддерживаются `resnet18`,
  `resnet34`.
- **Вход:** 3 или 4 канала. При 4 каналах первый conv-слой расширяется: копия
  RGB-весов + нулевая инициализация 4-го канала.
- **Голова:** GAP → Dropout → Linear(NUM_LABELS).
- **Чекпоинт:** `{“model_state_dict”: ..., “args”: ...}`.

### Конфиг лучшего достигнутого результата (image-only)

- Скор: **~0.51 P@10 = R@10** (val=30 изображений, фиксированный seed).
- efficientnet_b0, RGB, 224×224.
- BCE без pos_weight, без focal loss.
- Adam lr=1e-4, weight_decay=5e-4, dropout=0.3, batch_size=64.
- Только реальная разметка (~200 изображений), без псевдо.
- aug_strength=`mild`: RandomResizedCrop(0.92-1.0), rot=15°,
  ColorJitter(0.15/0.15/0.10, **hue=0**).

### Псевдо-разметка: алгоритм

**Файл:** `importance/pseudo_importance.py` (исторический, удалён из текущей кодовой базы)

Два сигнала:

1. **Робастный z-score:** `z_k(i) = (x_k(i) − median_k) / (MAD_k + eps)`
   по каждому признаку k. Чем выше |z|, тем больше вклад в скор важности.

2. **Приор по метаданным:** ключевые слова из полей diagnosis/structure
   добавляют фиксированные веса к меткам. Пример: «ретикуляр*» → +1.0 к
   texture, +0.9 к pigmentation; «симметрич*» → +1.2 к asymmetry.

`mode=”combined”`: итоговый скор = `z_weight * |z|_normalized + prior_weight *
meta_prior`. **Эмпирически не пригодна для прямого обучения top-k ранкера** —
смешивание с экспертной разметкой опускает P@10 с 0.40 до 0.05.

## Технические проблемы и их решения

### Утечка RAM (~100 MB/батч при длительном обучении)

- **Симптом:** RSS процесса растёт линейно, на ~30-й эпохе OOM.
- **Диагностика:** `tracemalloc` с фоновым потоком, снимающим топ аллокаторов
  каждые 30 с. Python-heap стабилен (~920 MB), но RSS растёт
  (2552→3734→3964 MB). Утечка в C/C++-библиотеках (Pillow, возможно
  DataParallel `replicate.py`), невидима для tracemalloc.
- **Решения:**
  1. `pin_memory = num_workers > 0` — при `num_workers=0` отключить
     `pin_memory`, иначе утечка host-буфера.
  2. `_malloc_trim()` через ctypes вызывается периодически в train/val циклах —
     возвращает свободные страницы ОС.
  3. Явный `del` + `gc.collect()` в конце эпохи.
  4. **Contiguous numpy-кэш изображений** — один массив `(N, H, W, 3)` uint8
     вместо N отдельных PIL-объектов. Реализовано в
     `_preload` в датасет-классе (contiguous numpy-кэш).

### Ошибка `'numpy.ndarray' has no attribute 'seek'`

- **Причина:** `extraction/segmentation.py::main()` вызывался с numpy-массивом
  вместо пути. YOLO ожидает путь или PIL-объект. Также YOLO + UNet
  перезагружались на каждый вызов при батчевой генерации.
- **Фикс:** `segment_with_loaded_yolo` принимает уже загруженную модель.

### Ошибка `cannot select an axis to squeeze out which has size not equal to one`

- **Причина:** `transform_4ch` ожидал 4 канала, но `ImportanceDataset` молча
  возвращал 3 канала при отсутствии маски.
- **Фикс:** при `use_mask_channel=True` всегда производится 4-канальное
  изображение — нулевая маска подставляется при её отсутствии. Флаг `_has_mask`
  для аудита.

### Регрессия к P@10=0.23 после успешного 0.45

- **Причина:** при перезапуске часть параметров упала к дефолтам
  (batch_size=16, wd=1e-3, dropout=0.4 вместо 64 / 5e-4 / 0.3).
- **Урок:** все гиперпараметры должны быть явно зафиксированы в
  конфиге/ноутбуке, нельзя полагаться на дефолты.

## Ограничения и открытые направления

### Текущие ограничения

- **Потолок при 200-400 аннотациях:** реалистичная оценка для image-only ветки
  ~0.55–0.57 P@10. val=30 даёт шум ±0.02 — выигрыши меньше этого
  статистически незначимы.
- **Слишком широкое пространство меток:** при ручной разметке стабильно
  используется пул ~25 признаков из 56. Остальные — «мёртвые» метки без
  положительных примеров, разбавляющие BCE-лосс. Это наблюдение подтвердилось
  сжатием до 24 активных меток в tabular-ветке.

### Таблица открытых направлений

| Направление | Ожидаемый выигрыш | Стоимость |
|---|---|---|
| Больше аннотаций (→500) | +5-10 pp | Высокая (ручной труд) |
| Сжатие пространства меток 56→25 | +3-5 pp | Низкая (код) |
| K-fold CV | Снижение шума оценки ±0.02 → ±0.005 | Средняя (время ×5) |
| TTA (hflip + multi-crop) | +1-2 pp | Низкая |
| Больший бэкбон (efficientnet_b3) + 288×288 | +2-4 pp | Средняя (VRAM) |
| Self-training с реальной моделью | +3-5 pp | Средняя |
| Маски на высоком разрешении | Неясно | Средняя |

## Инструмент ручной разметки

**Файл:** [annotation/app.py](../annotation/app.py), шаблоны в
[annotation/templates/](../annotation/templates/), статика в
[annotation/static/](../annotation/static/)

Flask + vanilla HTML/JS/CSS. Single-page app без фреймворков и сборки.

- Метки сгруппированы по 6 категориям (Общие, Цвет глобальный, Цвет локальный,
  Форма, Граница, Текстура).
- **Лимит в 10 чекбоксов технически enforced** — после 10 выбранных оставшиеся
  блокируются. Отражает формат экспертной разметки (ровно top-10).
- Ранее сохранённые аннотации предвыбраны при возврате к изображению.
- Клавиши: Enter = сохранить, стрелки = навигация.
- **Формат выхода:** CSV `annotations.csv` с полями `image_path` и
  `important_labels` (JSON-строка, например
  `[“asymmetry:умеренная”, “texture:неоднородная”, ...]`). Атомарная запись
  через temp-файл + `os.replace`.
- **Резюмирование:** при старте пропускает уже размеченные `image_path`.

Источники данных для UI:
- `LABEL_NAMES` из [config/importance_config.py](../config/importance_config.py)
- `FEATURE_ROUTING` из [config/config.py](../config/config.py)
- `_COMPOUND_LABELS` в [annotation/app.py](../annotation/app.py) — маппинг
  категорий для составных меток (asymmetry, borders, palette, и т.д.),
  которые не входят в `FEATURE_ROUTING`.

```bash
python annotation/app.py --csv features_dataset_bucket.csv --output annotations.csv --port 5050
```
