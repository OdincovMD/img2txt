# Шаг 2. Бакетизация признаков

**Основные файлы:** [bucketing/feature_bucketing_batch.py](../bucketing/feature_bucketing_batch.py), [bucketing/threshold_rules.py](../bucketing/threshold_rules.py), [bucketing/schema.py](../bucketing/schema.py), [config/threshold_config.py](../config/threshold_config.py), [analysis/feature_metadata.py](../analysis/feature_metadata.py), [analysis/results/distribution_report.json](../analysis/results/distribution_report.json), [analysis/results/scalar_thresholds.json](../analysis/results/scalar_thresholds.json), [analysis/results/label_distribution.json](../analysis/results/label_distribution.json)

## Роль шага

Шаг 2 берет численные признаки из шага 1 и переводит их в **клинически
интерпретируемые категориальные метки**.

На входе этого шага признаки еще выражены числами:

- округлость;
- контраст;
- вариабельность оттенка;
- локальные цветовые дельты;
- текстурные показатели;
- геометрические коэффициенты.

На выходе появляются метки вида:

- `shape:овальная`
- `borders:фестончатые`
- `contrast:выраженный`
- `texture:преимущественно однородная`

Именно эти метки потом:

- используются как интерпретируемое описание случая;
- становятся рабочим пространством признаков для шага 3;
- попадают в prompt шага 4.

Логически шаг 2 отвечает на вопрос:

> как перевести численное описание очага в ограниченный и читаемый клинический
> словарь признаков

## Что является входом

На вход шаг 2 получает:

- базовые численные признаки шага 1;
- составные агрегаты шага 1.

То есть шаг 2 уже не работает с изображением напрямую. Он работает с табличным
представлением случая.

## Что является выходом

На выходе формируются два связанных представления:

- словарь клинических меток `feature:value`;
- плоские bucket-поля `bucket_<feature>=value`.

Первое представление нужно для интерпретации человеком и для генерации текста.
Второе — для табличных моделей и аналитики.

## Главная идея шага

Шаг 2 не пытается улучшить или переоценить признаки. Его задача другая:

1. выбрать смысловую шкалу для каждого признака;
2. разбить ее на клинически осмысленные состояния;
3. сопоставить численное значение одному из этих состояний;
4. зафиксировать результат в читаемой категориальной форме.

То есть бакетизация — это слой **семантического сжатия**:

- меньше размерность;
- выше интерпретируемость;
- проще связать признаки с языком врача и с генерацией текста.

## Как логически устроена бакетизация

### 1. У каждого признака есть своя собственная шкала

Бакетизация не использует один универсальный порог для всех признаков. Для
каждой оси определяется собственная логика разбиения.

Примеры:

- округлость переводится в `округлая`, `овальная`, `неправильная`;
- контраст с кожей — в `низкий`, `умеренный`, `выраженный`;
- текстурная однородность — в `преимущественно однородная`,
  `умеренно неоднородная`, `неоднородная`.

### 2. Часть меток строится прямым пороговым правилом

В простейшем случае:

- есть одно численное значение;
- есть несколько интервалов;
- каждому интервалу соответствует метка.

Так строятся многие признаки формы, размера, цветового контраста и текстуры.

### 3. Часть меток строится по составному правилу

Некоторые клинические категории нельзя надежно выразить одним числом, поэтому
они строятся как логика поверх нескольких признаков.

Например:

- характер границы использует не только округлость, но и сложность контура;
- пигментация зависит от сочетания темных, красных, синих и белесых участков;
- наличие ободка определяется не абсолютной яркостью, а разницей между
  внутренней зоной и краем.

Здесь шаг 2 уже не просто применяет порог, а собирает клиническую категорию из
нескольких сигналов.

## Какие группы меток формируются

### 1. Форма и геометрия

Эта группа описывает общий силуэт и размер:

- `shape`
- `elongation`
- `area`
- `perimeter`
- `eccentricity`
- `solidity`
- `extent`

По смыслу она отвечает на вопрос:

> насколько очаг компактен, вытянут, плотен и близок к регулярной форме

### 2. Граница и контур

Эта группа описывает характер края:

- `borders`
- `rim`
- `convexity`
- `radial_variance`
- `fractal_dimension`
- `perimeter_area_ratio`
- `lobulation`

Именно здесь количественная сложность контура превращается в клинические
формулировки вроде ровных, неровных, фестончатых границ и выраженной
дольчатости.

### 3. Цветовой профиль

Эта группа описывает цвет очага и его отличие от кожи:

- `contrast`
- `palette`
- `pigmentation`
- `dominant_hue`
- `color_homogeneity`
- `color_balance_*`
- `color_distance_*`

Она отвечает на вопросы:

- насколько очаг контрастен;
- насколько его палитра однотонна или полихромна;
- какой оттенок преобладает;
- насколько цвет однороден внутри очага.

### 4. Локальные различия и асимметрия

Эта группа описывает неоднородность распределения признаков:

- `asymmetry`
- `delta_*`

Через нее система фиксирует различия между:

- центром и периферией;
- левой и правой половинами;
- верхом и низом;
- внутренней частью и краем.

### 5. Текстура и структура

Эта группа описывает внутренний рисунок очага:

- `texture`
- `texture_coarseness`
- `structure_order`
- `glcm_*`
- `lbp_*`

Здесь количественные текстурные показатели переводятся в язык однородности,
грубости, хаотичности и структурной упорядоченности.

## Как подбирались бакеты

Этот шаг настраивался не за один проход. Бакеты и пороги многократно
пересматривались, а их распределения анализировались на полном наборе данных.

Рабочая логика подбора была такой:

1. взять численные признаки после шага 1;
2. посмотреть их реальные распределения;
3. проверить, как предлагаемые пороги делят выборку;
4. убрать пустые, слишком редкие и бесполезные бакеты;
5. скорректировать шкалы так, чтобы они одновременно были:
   - клинически осмысленными;
   - статистически работоспособными;
   - пригодными для шага 3.

То есть конфигурация бакетов здесь не теоретическая и не “взята с потолка”.
Она была доведена до рабочей формы через последовательную правку порогов и
проверку их поведения на данных.

## На что опирался подбор порогов

### 1. Реальные распределения признаков

Для каждого признака анализировались:

- средние значения;
- стандартные отклонения;
- квартили;
- хвосты распределения;
- фактические доли случаев в каждом бакете.

Это позволяло видеть:

- какие интервалы слишком широкие;
- какие бакеты почти пустые;
- где пороги слишком рано или слишком поздно разделяют данные.

Артефакт с такими сводками:

- [analysis/results/distribution_report.json](../analysis/results/distribution_report.json)

### 2. Скалярные правила для составных клинических понятий

Для составных признаков отдельно подбирались специальные пороги, например для:

- контраста центр–периферия;
- наличия ободка;
- агрегированной однородности цвета;
- пигментации;
- границ;
- дольчатости.

Эти значения зафиксированы отдельно, потому что они используются как правила
более высокого уровня, а не как обычные интервальные шкалы.

Артефакт:

- [analysis/results/scalar_thresholds.json](../analysis/results/scalar_thresholds.json)

### 3. Итоговое распределение самих меток

После выбора порогов анализировалось уже не только распределение чисел, но и
распределение итоговых категориальных меток:

- какие метки реально часто встречаются;
- какие практически не используются;
- какие перегружают пространство признаков;
- какие оказываются полезными и живыми.

Артефакт:

- [analysis/results/label_distribution.json](../analysis/results/label_distribution.json)

## Какие типовые проблемы исправлялись в ходе настройки

В процессе правки бакетов приходилось решать несколько повторяющихся проблем.

### 1. Пустые или почти пустые бакеты

Если интервал почти не содержал наблюдений, такой бакет был бесполезен:

- он не помогал клинической интерпретации;
- он не помогал обучению;
- он только раздувал пространство меток.

Такие шкалы упрощались или сдвигались.

### 2. Бакеты, в которые попадало почти всё

Обратная проблема — когда почти вся выборка оказывалась в одной категории.
Тогда бакет переставал различать случаи и терял практический смысл.

В таких случаях пороги пересматривались, чтобы вернуть разделяющую способность.

### 3. Пороги, не соответствующие диапазону признака

Для части признаков в ранних вариантах шкалы могли плохо соответствовать
реальному диапазону данных. После анализа распределений такие случаи
исправлялись: интервалы приводились к фактическому поведению признака на
датасете.

### 4. Избыточно широкий словарь меток

Даже если отдельная шкала выглядела логичной сама по себе, в сумме это могло
давать слишком широкий и шумный словарь.

Поэтому шаг 2 настраивался не только “по одному признаку”, но и на уровне всей
системы категорий, которые потом используются в шагах 3 и 4.

## Почему итоговая конфигурация лежит в папке `analysis`

Финальная рабочая конфигурация бакетов была зафиксирована не только в коде
правил, но и в аналитических артефактах.

Это важно по двум причинам:

- можно проверить, почему выбран именно такой порог;
- можно увидеть, как этот порог реально делит датасет.

Именно поэтому в качестве итоговой опоры для шага 2 нужно смотреть не только
в `config/threshold_config.py`, но и в артефакты из `analysis/results`, где
видно поведение этой конфигурации на данных.

## Почему шаг 2 критичен для следующих этапов

Дальнейшие шаги работают не с сырыми числами, а уже с этим категориальным
пространством.

Это означает:

- шаг 3 ранжирует важность именно среди бакетизированных клинических признаков;
- шаг 4 строит текст именно по этим меткам.

Если бакетизация неудачна, то:

- важные различия между случаями могут потеряться;
- пространство признаков становится шумным;
- генерация текста получает плохую семантическую основу.

## Что дает шаг 2 следующему этапу

Для шага 3 результат шага 2 — это рабочее пространство категориальных
признаков, внутри которого можно оценивать важность, отбирать top-k и
отбрасывать шум.

Поэтому шаг 2 является не просто переводом чисел в слова, а критическим
промежуточным слоем между измерениями шага 1 и прикладным клиническим языком,
с которым дальше работает весь пайплайн.

## Детали реализации

### Составные правила — таблица

| Правило | Входные признаки | Логика |
|---|---|---|
| `_asymmetry` | Σ\|Δ_H/S/V по центр-периферия, лево-право, верх-низ\| | Правило A из ABCD. Порог — `asymmetry_agg`. |
| `_borders` | `circularity` + `perimeter_area_ratio` | «ровные» / «умеренно неровные» / «фестончатые». Правило B. |
| `_palette` | `dominant_colors_lesion` | Подсчёт «визуально различных» оттенков через `_compute_palette_variety`: сортировка H, счёт разницы >15°. |
| `_pigmentation` | `percent_dark/red/blue/white_pixels` | Приоритизация: белые > красно-синие > темнота. |
| `_elongation` | `aspect_ratio` + `eccentricity` | Линейная комбинация как score. |
| `_color_homogeneity` | `std_H/S/V` + `entropy_H` | Нормированная сумма. |
| `_lobulation` | `radial_variance` + `convexity` + `perimeter_area_ratio` | Score ∈ [0,1], три уровня. |
| `_dominant_hue` | `mean_H` + корректировка через `color_balance_R/G` | Основной оттенок + override на «зеленоватый». |
| `_pigment_inclusions` | `percent_red/blue/white_pixels` | Список включений (не строка). |
| `_rim` | `delta_V_inner_rim` | Светлый/тёмный ободок по знаку Δ. |

### Связь конфигурационных файлов

Три конфига связаны между собой:
`LABEL_NAMES ⊇ ключи составных правил + подмножество FEATURE_ROUTING`. При
изменении словаря меток нужно синхронизировать все три и перегенерировать
бакетизированный датасет:

| Файл | Роль |
|---|---|
| [config/config.py](../config/config.py) | `FEATURE_ROUTING: Dict[str, Tuple[category, russian_name, unit]]` — регистр 60+ признаков. Источник истины о том, что вообще существует в системе. |
| [config/threshold_config.py](../config/threshold_config.py) | `THRESHOLDS` + `SCALAR` — пороги и константы для составных правил. Источник истины для шага 2. |
| [model/config.py](../model/config.py) | `LABEL_NAMES` (24 активных метки), `NUM_LABELS`, `LABEL_TO_IDX`. Источник истины для шага 3. |

### Публичное API

- `features_to_labels(features: dict) -> dict` — один образец, возвращает
  словарь `feature:value`.
- `row_to_labels(row)` — обёртка для `df.apply`.
- `bucket_features_batch(df)` — батчевый вход, добавляет колонки `labels`,
  `features_organized`, `labels_json`.
