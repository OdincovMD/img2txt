# Шаг 3. Логика ранжирования важных признаков

Документ описывает **логику третьего шага пайплайна** в его текущем рабочем
виде: ranking на основе chain-модели, работающей в режиме `selected_only`.


Основные источники:

- `main:model/model.py`
- `main:model/inference.py`
- `main:model/config.py`
- `main:model/run.py`

Сервисная адаптация:

- `service/app/pipeline_steps/step3_ranking/ranking.py`
- `service/app/pipeline.py`

## Зачем нужен шаг 3

После шага 2 у нас уже есть интерпретируемый набор клинических меток:

- форма;
- границы;
- пигментация;
- контраст;
- оттенок;
- локальные перепады;
- текстура;
- и другие категориальные признаки.

Но полный список этих меток еще не отвечает на главный практический вопрос:

> какие из них действительно стоит вынести в итоговое описание как наиболее
> важные для данного конкретного случая

Именно это и делает шаг 3.

Он не генерирует текст и не меняет сами метки шага 2. Его задача —
**упорядочить признаки по важности** и вернуть компактный top-k набор.

## Что является входом

На вход шаг 3 получает представление случая после первых двух этапов:

- численные признаки шага 1;
- bucket-метки шага 2;
- словарь категориальных лейблов, из которых потом можно собрать
  человекочитаемый результат.

Логически шаг 3 работает уже не с изображением, а с **табличным описанием
случая**.

## Что означает `selected_only`

В текущей рабочей схеме шаг 3 не пытается ранжировать весь возможный словарь
признаков. Он работает только по **заранее отобранному подмножеству целевых
меток**.

Именно это здесь и имеется в виду под `selected_only`:

- модель предсказывает важность только для выбранного рабочего набора меток;
- все остальные признаки не входят в целевое пространство ранжирования;
- на выходе мы получаем top-k именно внутри этого сокращенного словаря.

Практический смысл такой:

- меньше шумовых категорий;
- выше устойчивость ранжирования;
- итоговый список ближе к реально нужным признакам для описания.

В коде это отражено через фиксированный список `LABEL_NAMES`, с которым
работает чекпоинт и инференс.

Источники:

- `main:model/config.py`

## Что является выходом

Выход шага 3 — это список `important_labels`, то есть top-k наиболее важных
признаков для конкретного случая.

Формат результата:

- `shape:овальная`
- `borders:умеренно неровные`
- `contrast:выраженный`

То есть шаг 3 не создает новые признаки. Он выбирает наиболее значимые
элементы из уже существующего категориального пространства.

## Главная идея шага

Логика шага построена так:

1. взять структурированное описание очага;
2. оценить вероятность важности для каждой целевой метки из `selected_only`;
3. учесть зависимости между метками через classifier chain;
4. отсортировать метки по score;
5. вернуть top-k самых важных.

Иными словами, шаг 3 решает не задачу "есть ли вообще такой признак", а задачу

> насколько этот признак должен попасть в список наиболее важных для текущего
> случая

## Почему здесь нужен именно ranking, а не просто классификация

В одном случае у образования может быть сразу несколько релевантных признаков.
Причем важность этих признаков не бинарна в прикладном смысле:

- часть признаков центральные;
- часть второстепенные;
- часть можно вообще не выносить в итоговое описание.

Поэтому шаг 3 мыслится как ранжирующий слой:

- не один лучший класс;
- не полный необработанный список;
- а приоритетный набор top-k признаков.

Это особенно важно, потому что шаг 4 потом строит текст именно по этому
сжатому приоритетному контексту.

## Как логически устроена модель на этом шаге

### 1. Для каждой целевой метки считается score важности

Внутри `selected_only`-пространства каждая метка получает численный score.

Этот score интерпретируется не как "истина в последней инстанции", а как мера
приоритета:

- чем выше score;
- тем выше шанс, что метка должна войти в финальный top-k.

После этого все целевые метки сортируются по score.

### 2. Модель работает как classifier chain

Ключевая логика текущей схемы в том, что предсказания по меткам делаются не
полностью независимо друг от друга.

Используется **цепочка классификаторов**:

- сначала предсказывается одна метка;
- затем следующая модель получает исходные признаки и предсказания предыдущих;
- потом следующая получает еще более полный контекст;
- и так далее по цепочке.

Это нужно потому, что важные признаки в клиническом описании часто связаны
между собой:

- одни сочетания усиливают вероятность других;
- некоторые признаки естественно сосуществуют;
- некоторые структурные паттерны лучше интерпретируются в комбинации.

Именно поэтому chain-модель логически лучше соответствует задаче, чем набор
полностью независимых бинарных решений.

Источники:

- `main:model/model.py`

### 3. На инференсе цепочка разворачивается последовательно

Для нового случая шаг 3 работает так:

1. строит входную табличную матрицу;
2. подает ее в первую модель цепочки;
3. сохраняет ее предсказание как дополнительный признак;
4. передает расширенный набор признаков в следующую модель;
5. повторяет это до конца цепочки.

В результате итоговый score каждой поздней метки учитывает не только
первичный профиль случая, но и уже предсказанную структуру соседних важных
признаков.

## Какие признаки получает модель на вход

В рабочем пайплайне шаг 3 использует табличное представление случая.

На вход могут входить:

- численные признаки шага 1;
- агрегированные численные признаки шага 1;
- bucket-представление шага 2 по выбранному рабочему набору меток.

В сервисной сборке это выражено так:

- базовые numeric features берутся из `FEATURE_COLUMNS`;
- составные numeric features берутся из `COMPOSITE_FEATURE_COLUMNS`;
- bucket-колонки для модели собираются в логике `selected_only`, то есть по
  упорядоченному набору целевых меток.

Важно, что модель работает не с произвольным сырым JSON, а со строго собранной
векторной формой, согласованной с чекпоинтом.

Источники:

- `main:model/model.py`

## Почему шаг 3 привязан к чекпоинту

Логика шага 3 определяется не только кодом, но и содержимым чекпоинта.

Чекпоинт фиксирует:

- набор моделей цепочки;
- список целевых меток;
- порядок цепочки;
- набор входных колонок;
- feature set;
- при необходимости калибровочный bias.

Это означает, что шаг 3 логически воспроизводим только вместе со своим
чекпоинтом: именно он определяет, какие признаки считаются, в каком порядке
предсказываются цели и как интерпретировать score.

## Зачем нужна калибровка bias

После получения score система может применять калибровочный сдвиг по меткам.

Логически это не новая модель, а корректировка распределения выбора:

- чтобы часть меток не оказывалась системно недовыбранной;
- чтобы распределение top-k было ближе к целевому рабочему пространству;
- чтобы итоговое ранжирование было более сбалансированным.

То есть здесь корректируется не сам факт наличия признака, а его шанс попасть
в итоговый приоритетный список.

Источник:

- `main:model/model.py`
- `main:model/run.py`

## Как из score получается итоговый список

После того как все целевые метки получили score:

1. они сортируются по убыванию;
2. берутся первые `k`;
3. каждая метка связывается со своим человекочитаемым bucket-значением;
4. формируется список `feature:value`.

Например, модель ранжирует не абстрактную сущность `shape`, а в результате
возвращает именно готовую форму вроде `shape:овальная`, если соответствующее
bucket-значение у текущего случая равно `овальная`.

Это важная часть логики шага:

- модель оценивает важность оси признака;
- итог пользователю и шагу 4 отдается уже как конкретная интерпретируемая
  метка.

## Что шаг 3 не делает

Шаг 3 не:

- извлекает признаки из изображения;
- придумывает новые клинические категории;
- генерирует описание;
- заменяет экспертную формулировку свободным текстом.

Его роль уже и точнее:

- отобрать;
- упорядочить;
- сократить пространство признаков до действительно важных.

## Что шаг 3 дает следующему этапу

Для шага 4 результат критичен, потому что генерация опирается не на весь
список признаков, а на уже отобранный приоритетный контекст.

Без этого слоя генерация получила бы:

- слишком много признаков;
- слишком шумный сигнал;
- слабую иерархию важности.

После шага 3 генерация получает:

- короткий;
- интерпретируемый;
- уже ранжированный список клинически значимых меток.

Именно поэтому шаг 3 является логическим фильтром между полной
признаковой картиной случая и финальным текстом.
